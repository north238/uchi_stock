# UchiStock 改修要件定義書（MVP / フェーズ0）

最終更新: 2026-07-21
対象読者: 実装を担当するAIエージェントおよびレビュアー（開発者本人）
上位文書: `docs/01_concept.md`（目的・検証計画はそちらを正とする）

## 1. 背景と目的

UchiStock は「日用品の購入時に『家にまだあるか』を家族に確認する手間をなくす」アプリである。
本改修は、既存実装の軸を「在庫台帳（数量管理）」から「購買判断（ステータス＋購入履歴）」へ移すことを目的とする。

本書のスコープは **フェーズ0（MVP完成、〜2026-06-30）** のみ。
すべての実装判断は次の基準で行うこと:

> その変更は「買ってよいかの判断を速く・確かにする」か？

## 2. 変更概要（As-Is → To-Be）

| 観点       | As-Is（現状）          | To-Be（変更後）                                                            |
| ---------- | ---------------------- | -------------------------------------------------------------------------- |
| 在庫の表現 | quantity（整数、必須） | **status（ある/少ない/ない）が主役**。quantity は任意入力の参考情報に降格  |
| 購入の記録 | なし                   | 「買った」ワンタップで購入履歴を記録                                       |
| 一覧画面   | テーブル型、数量中心   | カード型、**品名・ステータス・前回購入○日前** 中心。一覧上でワンタップ操作 |
| 並び順     | 固定                   | 切替可能（デフォルト: ステータス順）                                       |

## 3. データ要件

### 3.1 items テーブルの変更（新規マイグレーション追加。既存マイグレーションは編集しない）

- `status` カラムを追加する
  - 型: string、値は `in_stock`（ある）/ `low`（少ない）/ `out`（ない）の3値のみ
  - default: `in_stock`。既存レコードはマイグレーション時に `in_stock` で埋める
- `quantity` を nullable に変更する
  - バリデーションは `nullable|integer|min:0` に変更（現状の `required ... min:1` を廃止）

**設計原則: status が常に正。quantity は参考表示のみで、いかなるロジック（並び順・判定・自動更新）にも使用しない。**

### 3.2 purchase_histories テーブルの新規作成

| カラム       | 型         | 備考                                  |
| ------------ | ---------- | ------------------------------------- |
| id           | bigint PK  |                                       |
| item_id      | FK → items | アイテム削除時は履歴も削除（cascade） |
| user_id      | FK → users | ユーザー削除時 null（nullOnDelete）   |
| purchased_at | datetime   | 記録時は現在日時を設定                |
| timestamps   |            |                                       |

- 履歴は削除・編集のUIを作らない（記録専用。将来の購入周期推定の資産とするため）
- 「前回購入」は当該アイテムの `purchased_at` 最新値から算出する
- **アイテム新規登録時、登録日時を `purchased_at` として購入履歴を1件自動作成する**（登録＝購入とみなす。2026-07-24 決定）。ステータスはフォーム選択値のまま保存し、F-2 の「買った」記録（`ItemService::recordPurchase`）のように `in_stock` へ強制変更はしない
- 「前回購入: 購入記録なし」の表示分岐（`days_since_purchase === null`）は上記自動作成により通常到達しなくなるが、将来の履歴削除機能等で到達しうるため防御的に残す

## 4. 機能要件と受け入れ条件

### F-1 ステータスのワンタップ変更

一覧画面の各アイテム上で、画面遷移なしにステータスを変更できる。

受け入れ条件:

- 一覧のカード上で「ある/少ない/ない」を1タップで切り替えられる（編集画面への遷移なし）
- 変更は即時保存され、リロード後も保持される
- 変更後、並び順がステータス順の場合は表示位置が追従する（即時 or リロード時、実装は問わない）

### F-2 「買った」ワンタップ記録

一覧画面の各アイテムに「買った」ボタンを置く。

受け入れ条件:

- タップすると `purchase_histories` に1レコード追加される（purchased_at = 現在日時、user_id = 操作ユーザー）
- 同時に当該アイテムの status が `in_stock` に更新される
- 一覧の当該カードに「前回購入: 今日」と表示される
- 誤タップ対策として、タップ直後に取り消し（Undo）可能にするか、確認を挟むこと（方式は任せる。ただし操作は最大2タップまで）

### F-3 一覧画面の判断特化リデザイン

既存のテーブル型一覧を、モバイル前提のカード型に統一する。

受け入れ条件:

- 各カードに **品名 / ステータス / 前回購入から○日**（購入記録がない場合は「購入記録なし」）が表示される
- ジャンル・保管場所・メモ・quantity は補助情報として小さく表示するか、詳細で確認する扱いとする
- 並び順はデフォルトで **ステータス順（ない → 少ない → ある）**、同ステータス内は前回購入が古い順（購入記録なしを先頭）
- 並び順を「前回購入が古い順」に切り替えるUIがある（選択状態の永続化は不要）
- 既存の検索・絞り込みがあれば維持する
- スマートフォン表示を主とし、1画面で複数アイテムの状態が判断できる密度にする

### F-4 登録・編集フォームの調整

受け入れ条件:

- 登録・編集フォームに status の選択（3値）が追加される。デフォルトは `in_stock`
- quantity は任意入力になる（未入力でも保存できる）
- 登録完了後は一覧（`items.index`）へ遷移し、「〇〇を登録しました」のフラッシュメッセージを表示する（2026-07-24 決定。従来の「登録画面に留まりフォームをリセット」という挙動から変更）
- 登録画面のヘッダーに一覧へ戻る導線を設置する（遷移先は `items.index` 固定。ブラウザ履歴の back には依存しない）
- 登録時、登録日時を `purchased_at` として購入履歴を1件自動作成する（登録＝購入とみなす。2026-07-24 決定）。ステータスはフォームで選択した値をそのまま保存し、`in_stock` へ強制変更はしない
- 音声入力による登録フローは現状のまま動作する（デグレなし）。※音声入力機能自体は削除予定（§5 参照）のため、この規定は機能が存在する間のみ有効

## 5. 変更禁止事項（エージェントへの明示的な制約）

以下には**一切手を加えないこと**。関連ファイルのリファクタリング・整形・「ついでの改善」も禁止する。

- 認証まわり（Laravel Breeze / セッション認証）
- グループ機能（自動生成の仕組み含む）
- Docker 構成（docker-compose、各 Dockerfile）
- ジャンル・保管場所の管理機能

> **2026-07-24 追記**: 音声入力機能（`VoiceInput.tsx`、whisper サービス、`api.voice.transcribe`）は、対応する Whisper API が用意されておらず実質使用不可であることが判明したため、上記の変更禁止対象から除外し、**削除予定**の扱いに変更した。削除の実施は本書・`docs/03`・`docs/04`・`CLAUDE.md` のドキュメント更新が完了した後、別タスク（`docs/05` Phase 11）として着手する。ドキュメント更新前にコードを削除しないこと。

## 6. スコープ外（作らないもの）

以下は要望されても実装しない。提案も不要。

- 賞味期限・消費期限の管理
- 数量の自動増減・厳密な数量管理
- グループ招待・承認フローの仕上げ
- 「これ買う？」確認ボード、家族間チャット
- 通知（プッシュ・メール等）
- 購入周期の推定・「そろそろ無いかも」表示（フェーズ2以降の候補）
- 家族への確認回数のカウント機能（検証はアプリ外で記録する）
- PWA 化・オフライン対応

## 7. 非機能要件

- 一覧画面はスマートフォンで開いて3秒以内に判断材料が視認できること（初期表示の体感速度を優先し、重い集計はクエリ側で解決する）
- 前回購入日の算出で N+1 クエリを発生させないこと
- 既存テスト（`php artisan test`）が通ること。F-1, F-2 についてはFeatureテストを追加すること

## 8. 実装順序の推奨

1. マイグレーション2本（items.status 追加 + quantity nullable 化 / purchase_histories 作成）とモデル・リレーション
2. F-2「買った」記録のAPI＋F-1 ステータス変更のAPI（Featureテスト含む）
3. F-3 一覧画面のカード型リデザインと並び順
4. F-4 フォーム調整
5. 音声入力フローのデグレ確認

各ステップは独立してレビュー可能な粒度でコミットを分けること。

## 9. 完了の定義

- 受け入れ条件（F-1〜F-4）をすべて満たす
- 変更禁止事項に差分がない
- `php artisan test` がグリーン
- 開発者本人のスマートフォンで、一覧を開いて「買ってよいか」が判断できる状態になっている
