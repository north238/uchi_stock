# UchiStock コンセプト文書

最終更新: 2026-06-11

## 目的

> UchiStockは、日用品の購入時に「家にまだあるか」を家族に確認する手間をなくすアプリ。
> 正確な在庫数ではなく、購入履歴と大まかな状態から「買ってよいか」を判断できるようにする。

今後の機能追加・改修は、すべて「この判断を速く・確かにするか？」を基準に取捨選択する。

### 原体験

ネットで日用品を購入するたびに「これ、まだ家にあったっけ？」を家族に確認するのが手間だった。
確認しているのは在庫の個数ではなく「買ってよいかどうか」である。

### 前提条件（自分の実験で確定済み）

- 人間に正確な消費記録を期待する設計は成立しない（メモですら書き忘れた）
- したがって「使ったら減らす」方式の在庫管理は採用しない
- 精度を捨てて更新コストを下げることで、データの鮮度を保つ

## 設計原則

1. **正確さより鮮度**: 個数ではなく「ある / 少ない / ない」の3段階ステータスで管理する
2. **記録は購入時に集約**: 消費の記録は忘れるが、購入の記録は忘れにくい。「買った」のワンタップで購入日時を記録する
3. **判断材料は推定でよい**: 「前回購入から○日」が見えれば、買ってよいかの判断には十分
4. **価値が発生する瞬間に最適化**: ECサイトでカートに入れる直前、スマホで開いて3秒で判断できること

## ポジショニング

| 領域                   | 代表例                      | 限界                                           |
| ---------------------- | --------------------------- | ---------------------------------------------- |
| 家庭用在庫管理アプリ   | うちメモ、在庫ノート、zaico | 「使ったら手動でマイナス」方式は更新が続かない |
| 買い物リスト共有アプリ | 各種買い物リストアプリ      | 「買うと決めた後」しか扱わない                 |
| 家族グループLINE       | LINE                        | 確認の手間そのものが残る                       |

UchiStockは両者の間にある **「買うかどうか迷っている瞬間の判断材料を提供する」** 領域を取る。
音声入力・家族共有は単体ではもう差別化要素にならない。差別化は「更新が続く設計」と「判断特化のUI」で行う。

LINEで聞くより「聞かなくて済む」状態を作れたら勝ち。

## MVPスコープ

### ユーザーストーリー（これ一つだけ）

> ネットで日用品を買おうとした瞬間、スマホでアプリを開いて3秒で「買ってよいか」が分かる

### 追加するもの

1. **ステータス（ある / 少ない / ない）の導入** — 一覧の主役を数量からステータスに置き換える。数量は脇役に降格
2. **「買った」ワンタップ記録** — 購入日時を記録し、ステータスを「ある」に更新する。購入履歴はテーブルとして残す（履歴データは後から作れない。将来の購入周期推定の資産になる）
3. **一覧画面の判断特化リデザイン** — 品名・ステータス・前回購入から○日 が一目で分かるカード型。ステータス変更は一覧上でワンタップ。並び順は「ない→少ない→ある」または購入日が古い順

### 既存のまま活かすもの

認証、アイテムCRUD、音声入力（登録コスト削減装置として目的に合致）、グループ自動生成（一人利用は仮グループで成立済み）

### 意図的に作らないもの（第2段階以降）

賞味期限管理、厳密な数量増減、グループ招待・承認フローの仕上げ、「これ買う？」確認ボード、通知

## 検証計画（2026年6月版）

検証は直列で行う。仮説A「自分の確認の手間が減る」が崩れたら、仮説B「家族も使ってくれる」を試す意味はない。

### フェーズ0: 作り切る（〜6/30）

- MVPを完成させ、自分のスマホで使い始める
- **撤退条件**: 7/7までに自分が日常で使い始められていなければ、原因を記録して完了扱いとする
  （締切に1週間のバッファ。それでも動かないなら熱量の問題と判断する）

### フェーズ1: 一人で使う（7/1〜7/14）

- 自分一人で2週間使う
- 期間中、家族に在庫確認をしてしまった回数を記録する（体感ではなく記録で判定する）
- **合格条件**: 確認回数が記録上で減っている。かつ、購入時にアプリを開く習慣が2週間続いた
- **撤退条件**: 自分ですら開かなくなった場合。「なぜ開かなかったか」だけ書き残して終了する

### フェーズ2: 家族を巻き込む（7月後半〜、フェーズ1合格時のみ）

- 家族にステータス更新（ワンタップ）の入力を依頼する。アイテム登録・購入記録は自分の担当のまま、求める操作は一種類に絞る
- **合格条件**: こちらから頼まずに、家族による自発的な更新が週1回以上発生する
- **不合格時**: 即終了ではなく、原因を4分類でヒアリングする
  1. **気づかない** — アプリの存在を忘れている、開く動線がない → ホーム画面配置、PWA化
  2. **面倒** — ワンタップでも起動までの手数が重い → ログイン維持、表示速度改善
  3. **動機がない** — 更新しても本人にメリットが返らない → 更新が次の買い物に反映される実感づくり
  4. **タイミングが合わない** — 使い切った瞬間は手が塞がっている → 夜にまとめて聞く形式など入力タイミングの再設計
- 診断→改修→再検証2週間のループは **1回まで**。検証を延命に変えない
- それでも不合格なら、入力前提モデルは棄却し、**閲覧専用モデルへの縮退**か終了を判断する
  （フェーズ1に合格している限り、アプリの価値はゼロではない）

## このプロジェクトの位置づけ

- 燃料は「技術的好奇心」と「課題解決への好奇心」の両方。現在の軸（購買履歴・状態推定）は両者が同じ方向を向いている
- 購買履歴が貯まれば、購入周期の推定（「そろそろ無いかも」）という技術的な伸びしろがある
- 結果がどうあれ、検証して判断した形で終われるようにする。きれいに終われる設計は、続ける設計と同じくらい大事
